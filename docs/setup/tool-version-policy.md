# ツールのバージョン指定と更新方針

DF-06の一覧集約は完了している。今後は、検証環境との一致と設定の互換性が必要なツールから固定を検討する。全ツールの厳密固定は行わず、既存の指定を維持する。本書の追加固定候補は提案であり、設定への反映と実機確認は残件とする。

## 現在の指定と追加固定の候補

ツール一覧は`home/dot_config/mise/config.toml`で管理する。通常適用は`run_after_install-mise.sh`で不足を確認し、HOMEを対象に`mise install`する。スクリプト内に別のツール一覧や版指定は追加しない。

| 対象 | 現在の指定 | 当面の扱い・更新時の確認 |
| --- | --- | --- |
| lefthook | `2.2.2` | 厳密固定を維持。mise・CIの版とチェックサム・導入手順を同じPRで更新し、hook回帰テストを実行する |
| Node.js | `24` | メジャー系列を維持。npm系ツールとシェル初期化を確認してから系列を変更する |
| Python | `3.13`・`3.12` | 2系列を維持。初期認証前のOS側Python 3.11以上の準備とは分ける |
| Lua | `5.1` | 系列を維持。Neovim設定とLuaRocks補助処理を一緒に確認する |
| Yazi・Neovim | `latest` | 追加固定の優先候補。利用中のプラグインと設定全体が動く版を実機で確認してから決める |
| ShellCheck・shfmt・Bats | `latest` | CIとの版差を記録する。CI側はUbuntuのAPTを使うため、mise側だけ固定しても一致しない |
| age・sopsなどの秘密管理関連 | `latest` | 固定による修正版の取り込み遅延も考慮する。実秘密情報を使わない回帰検証と提供元の変更内容で判断する |
| その他のCLI・言語サーバー・ランタイム | 多くは`latest` | 当面維持。互換性の問題が確認されたツールから個別に固定を検討する |

`24`や`3.13`は完全な版固定ではない。同じ系列内でも導入時期によって版が変わる。`latest`も含め、現在の指定だけで全環境を同じ状態に再現できるとは扱わない。

Termux本体にはこのUbuntu向けmise設定を展開しない。Termuxのpkgで導入するmise本体、手動準備するlefthook、各バックエンドのAndroid互換性は別途確認する。

## 通常導入と更新を区別する

`mise install`は設定へツールを追加する操作ではない。通常適用では管理対象の設定に従い、展開先を`mise use -g`で書き換えない。[mise installの公式説明](https://mise.jdx.dev/cli/install.html)

`mise upgrade`は通常、設定の指定範囲内で更新する。`--bump`は範囲を越えて設定も更新するため、この運用では使用せず、変更案をソース側のPRにする。[mise upgradeの公式説明](https://mise.jdx.dev/cli/upgrade.html)

現行の`update_apps mise`は`mise outdated`の結果にかかわらず`mise upgrade`へ進む。更新対象をHOMEへ固定しておらず、起動したディレクトリのプロジェクト設定が影響し得る。ホームのツールだけを更新する保証はないため、利用者は実行場所と対象を確認する。これは静的解析で確認した制約で、実更新による再現は行っていない。

## 更新を行う順序

1. 対象ツールと設定の参照箇所、提供元の変更内容、対象CPU・OSの配布状況を確認する。最新版の導入成功を前提にしない。
2. 固定値や系列を変える場合は、作業ブランチでソースを編集する。更新前のソースのコミットと、秘密情報を含まないツールの版を記録する。
3. ソースのTOML解析と関連する既存テストを実行する。CI・mise・手順書が同じ版を必要とする場合は一緒に変更する。
4. PRの差分と必須チェックを確認する。実環境への適用・導入は別の操作として扱う。
5. 利用者が実機で対象ツールを準備し、実際の起動・キー操作・プラグインを確認する。失敗した場合は新しい版への切替を中止し、確認済みの指定へ戻す案をソースに作る。旧版の再取得可否は別途確認する。

更新候補の確認に`mise outdated`を使う場合も、外部への問い合わせがあり得るため、自動テストからは呼ばない。設定で許容される範囲の更新候補を表示するコマンドであり、すべてのツールの最新版を表示するとは限らない。[mise outdatedの公式説明](https://mise.jdx.dev/cli/outdated.html)

## 次の実装と受け入れ条件

| 残件 | 実装・検証の方針 |
| --- | --- |
| 更新対象の明確化 | `update_apps mise`をHOME対象にそろえる最小修正を検討する。作業ディレクトリに別設定があっても、ダミーmiseへHOME対象の引数が渡ることを確認する |
| 失敗の扱い | 現行のoutdated失敗後もupgradeへ進む仕様を維持するか決める。異常終了・後続処理・失敗集計をモックで確認する |
| 固定値の選定 | Yazi・Neovimの実機で動作する組合せを記録し、選定理由と戻し方をPRへ記載する。未確認の版を新しい基準として採用しない |
| 再現性の追加対策 | 必要性が確認された場合に限りlockfileを評価する。複数環境・CPU・バックエンドの対応確認を先行し、今回は追加しない |

既存の`tests/test_update_apps.py`はAPT側が中心で、mise更新の引数や失敗時の動作の検証は未実装。`tests/test_mise_helpers.py`の通常導入テストと区別して追加する。`make check`の成功だけで、実際の更新・配布物・プラグイン互換性が確認できたとは扱わない。
