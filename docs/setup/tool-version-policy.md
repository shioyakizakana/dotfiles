# ツールのバージョン指定と更新方針

DF-06の一覧集約は完了している。検証環境との一致と設定の互換性が必要なツールから固定する。全ツールの厳密固定は行わない。Yaziは公開依存を使った隔離起動を確認して26.9.1へ固定したが、実機操作や他の追加固定候補は残件とする。

## 現在の指定と追加固定の候補

ツール一覧は`home/dot_config/mise/config.toml.tmpl`で管理する。通常適用は`run_after_install-mise.sh`で不足を確認し、HOMEを対象に`mise install`する。スクリプト内に別のツール一覧や版指定は追加しない。

| 対象 | 現在の指定 | 当面の扱い・更新時の確認 |
| --- | --- | --- |
| lefthook | `2.2.2` | 厳密固定を維持。mise・CIの版とチェックサム・導入手順を同じPRで更新し、hook回帰テストを実行する |
| Node.js | `24` | メジャー系列を維持。npm系ツールとシェル初期化を確認してから系列を変更する |
| Python | `3.13`・`3.12` | 2系列を維持。初期認証前のOS側Python 3.11以上の準備とは分ける |
| Lua | `5.1` | 系列を維持。Neovim設定とLuaRocks補助処理を一緒に確認する |
| Nim | `2.4.2` | 公式リリースのURLとSHA256を環境別に固定。更新時は配布物とダイジェストを再確認し、Nim・nimble・nimlspを検証する |
| Yazi | `26.9.1` | 公開manifestの固定revisionと組み合わせ、初期化・描画を隔離環境で確認。個々の操作と各実機の確認は残件 |
| Neovim | `latest` | 現時点では固定せず、miseの一括更新時に他ツールとともに最新版へ更新する。プラグインの復旧には必要時のlockfileスナップショットを使う |
| ShellCheck・shfmt・Bats | `latest` | CIとの版差を記録する。CI側はUbuntuのAPTを使うため、mise側だけ固定しても一致しない |
| age・sopsなどの秘密管理関連 | `latest` | 固定による修正版の取り込み遅延も考慮する。実秘密情報を使わない回帰検証と提供元の変更内容で判断する |
| その他のCLI・言語サーバー・ランタイム | 多くは`latest` | 当面維持。互換性の問題が確認されたツールから個別に固定を検討する |

`24`や`3.13`は完全な版固定ではない。同じ系列内でも導入時期によって版が変わる。`latest`も含め、現在の指定だけで全環境を同じ状態に再現できるとは扱わない。

Termux本体にはこのUbuntu向けmise設定を展開しない。Termuxのpkgで導入するmise本体、手動準備するlefthook、各バックエンドのAndroid互換性は別途確認する。

## Proot版Ubuntuのnpm導入と起動確認

Proot版Ubuntuでは、実行可能な `~/.local/bin/mise` がある場合、Bash・Zshの起動時にそのディレクトリをPATHの先頭へ移す。更新処理も同じ場所を優先し、実行可能なmiseがなければエラーで停止する。これにより、Termux側のmiseでUbuntu向けツールを更新することを防ぐ。環境判定には既存の `prootUbuntu` フラグを使い、Termuxのフラグが有効な場合はこの処理を適用しない。

mise設定はchezmoiの `prootUbuntu` フラグに従い、Proot版Ubuntuの場合だけ `npm.package_manager = "npm"` と `npm.shell_out = true` を追加する。npm CLIによる導入とバージョン情報の照会を使い、ほかのUbuntu環境にはこの追加設定を出さない。Termux本体へのmise設定の展開除外も維持する。

通常導入・再適用と `update_apps mise` の更新成功後には、ホームのmise環境で `codex --version`、`oxlint --version`、`tsc --version` を順に確認する。確認には `MISE_AUTO_INSTALL=0` を指定し、コマンド欠落や非0終了を検出した時点で停止する。導入処理は後続の補助ツール確認へ進まず、更新処理はmise対象を失敗として集計する。指定されたほかの更新対象の処理は継続し、最終終了コードは1になる。

設定の適用だけで、既存の不完全な依存配置を修復したことにはならない。起動確認に失敗した場合は、エラーと対象版を確認し、必要な再導入を別途判断する。認証・秘密情報の取得や、自動での削除・再導入は行わない。

## Nimの配布物を固定する理由と更新手順

この節の導入・検証結果は2026-11-14時点の記録。後続のNimLSPの再ビルドと通常起動の確認は、[復旧手順](nimlsp-recovery.md)と[Neovimの依存・検証記録](neovim-dependencies.md)を参照する。

2026-11-14、Linux ARM64でNim 2.4.0の取得が404になる報告を受けた。従来の定義はx64向け一覧から版を選び、ほかのCPUにも同じ版のファイルがあると仮定してURLを生成していた。[公式の導入一覧](https://nim-lang.org/install.html)には2.4.0のLinux ARM64配布リンクがなく、2.4.2には存在した。

Nimは2.4.2に固定し、日付とコミットを含む公式リリースのURLを各環境へ指定した。SHA256は[GitHubのリリースAPI](https://api.github.com/repos/nim-lang/nightlies/releases/tags/2026-11-13-version-2-4-b27dcb4f70883978e984e427cc24b64eeb7c875f)の各asset.digestを使う。Linux ARM64のアーカイブへのHEADは200だったが、付随する.sha256のURLは404だったため、チェックサムURLの推測はやめた。全アーカイブの取得・展開・実行は未実施。

Linux・macOSはARM64とx64を指定する。Windows ARM64は従来と同じx64配布物を指定しており、ARM64ネイティブ対応を意味しない。Termux本体へは展開せず、proot内での実行も別途確認する。[miseのHTTPバックエンド仕様](https://mise.jdx.dev/dev-tools/backends/http.html)に従い、直接指定したchecksumを使用する。

### 版・URL・SHA256の更新

更新時は、先に公式一覧から各環境の配布物を確認する。同じリリースの版・URL・SHA256と、公開メタデータを記録したtests/test_nim_config.pyをまとめて更新し、回帰テストを実行する。版だけを変更すると別の配布物と組み合わさるため、個別には変更しない。

### Nimだけを適用・導入する手順

利用者が適用・導入する場合は、次の順でNimだけを対象にする。この手順をCodexは実行していない。その後、利用者からchezmoi applyと導入スクリプトによるNim導入成功の報告があった。

```shell
# 導入スクリプトを実行せず、miseの設定だけを展開する。
chezmoi apply --exclude=scripts "$HOME/.config/mise/config.toml"
mise --cd "$HOME" install nim@2.4.2
mise --cd "$HOME" exec nim@2.4.2 -- nim --version
```

その後、新しいシェルでcommand -v nimlspを確認し、Mason無効化モードのNeovimでNimの接続と診断を確認する。~/.nimble/binのPATH追加は利用者が行っており、この修正では変更していない。コンパイラ更新だけで既存nimlspの互換性まで確認したとは扱わず、必要な再ビルドはエラーを確認してから判断する。

### Nim固定時の隔離検証

修正前に回帰テストの不一致を確認し、修正後は3件すべて成功した。実HOMEの外にある/tmpの一時設定で、mise ls --no-global nim --jsonをMISE_OFFLINE=1にして実行し、2.4.2が未導入の版として選ばれた。同じ隔離環境のmise lockでも、全6環境のURLとSHA256が一致し、通信・導入なしで解決できた。生成したlockfileは一時領域だけに置き、リポジトリへは追加していない。HOME内の一時フォルダでは祖先の設定を探索するため、隔離確認には使わない。

make checkは静的検証、unittest全216件、Bats全18件が成功し、skipなし。修正時のCodex検証では実インストールを行っていない。その後のNim導入成功は利用者が確認した。この時点ではnimlspの接続は未確認だった。

## 通常導入と更新を区別する

`mise install`は設定へツールを追加する操作ではない。通常適用では管理対象の設定に従い、展開先を`mise use -g`で書き換えない。[mise installの公式説明](https://mise.jdx.dev/cli/install.html)

`mise upgrade`は通常、設定の指定範囲内で更新する。`--bump`は範囲を越えて設定も更新するため、この運用では使用せず、変更案をソース側のPRにする。[mise upgradeの公式説明](https://mise.jdx.dev/cli/upgrade.html)

`update_apps mise`は確認・更新の両方を`mise --cd "$HOME"`で実行する。起動したディレクトリのプロジェクト設定から離れ、HOMEを対象に通常の設定探索を行う。HOME配下の追加設定や環境変数による上書きもmiseの仕様に従うため、管理対象TOMLだけを読み込む保証とは区別する。

`outdated`が非0で終了した場合は`upgrade`を実行せず、mise更新を失敗として集計する。更新が非0で終了した場合も失敗とする。他の指定ターゲットの処理は継続し、いずれかが失敗した場合の最終終了コードは1。miseが見つからない場合の省略は維持する。

確認した[mise v2026.10.25の実装](https://github.com/jdx/mise/blob/v2026.10.25/src/cli/outdated.rs)では、更新候補の有無によらず通常は成功として返る。一方、バックエンドの確認失敗を警告だけで扱う場合もある。この修正はコマンドの非0終了を停止条件とし、警告文の文字列解析は行わない。終了コード0だけで全バックエンドの確認成功を保証するものではない。警告が出た場合は内容を確認し、実更新の成否も別に確認する。

## 更新を行う順序

1. 対象ツールと設定の参照箇所、提供元の変更内容、対象CPU・OSの配布状況を確認する。最新版の導入成功を前提にしない。
2. 固定値や系列を変える場合は、作業ブランチでソースを編集する。更新前のソースのコミットと、秘密情報を含まないツールの版を記録する。
3. ソースのTOML解析と関連する既存テストを実行する。CI・mise・手順書が同じ版を必要とする場合は一緒に変更する。
4. PRの差分と必須チェックを確認する。実環境への適用・導入は別の操作として扱う。
5. 利用者が実機で対象ツールを準備し、実際の起動・キー操作・プラグインを確認する。失敗した場合は新しい版への切替を中止し、確認済みの指定へ戻す案をソースに作る。旧版の再取得可否は別途確認する。

更新候補の確認に`mise outdated`を使う場合も、外部への問い合わせがあり得るため、自動テストからは呼ばない。設定で許容される範囲の更新候補を表示するコマンドであり、すべてのツールの最新版を表示するとは限らない。[mise outdatedの公式説明](https://mise.jdx.dev/cli/outdated.html)

## 追加固定に向けた残件

| 残件 | 実装・検証の方針 |
| --- | --- |
| 固定値の選定・見直し | Yaziは26.9.1の指定を維持し、見直す場合は[依存一覧と固定候補](yazi-dependencies.md)で互換性を確認する。その他の候補も確認済みの組合せと戻し方をPRへ記録する。Neovim本体はlatestを維持し、追加固定の対象に含めない |
| 再現性の追加対策 | 必要性が確認された場合に限りlockfileを評価する。複数環境・CPU・バックエンドの対応確認を先行し、今回は追加しない |

`tests/test_update_apps.py`はAPTとmiseの明示的更新をダミーで検証する。miseでは空白を含むHOMEと別プロジェクトを用意し、対象・実行順序・更新候補の表示・非0終了時の停止・失敗集計・mise欠落時の省略を確認する。`tests/test_mise_helpers.py`の通常導入テストとは区別する。`make check`の成功だけで、実際の更新・配布物・プラグイン互換性が確認できたとは扱わない。

NeovimのLSP・プラグイン・ビルド依存と確認範囲は[Neovim依存一覧](neovim-dependencies.md)を参照する。Mason依存の除去は確認済み環境・用途で完了している。本体はlatestを維持し、プラグインの復旧には必要時の手動スナップショットを使う。
